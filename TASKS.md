## Фоновые операции

В приложении сейчас нет ни одной фоновой задачи: все данные собираются только в момент
захода на страницу. Это главное ограничение всей статистики.

- [ ] **Фоновый сбор добычи** (планировщик готов, осталось вынести сбор из хендлера) — леджер `/characters/{id}/mining/` и цены Житы за день
      складывать в `mining_ledger` **раз в 15 минут** И **при открытии страницы**
      (сейчас работает только второе). Зачем: окно ESI ~30 дней и конечно, а без
      регулярного сбора история рвётся, если месяц не заходить в кабинет. Кэш леджера
      у ESI 600 с, так что 15 минут — это ровно один свежий ответ на цикл, лишнего
      трафика нет.
- [x] **Каркас планировщика** — `internal/sched`: горутина с тикером на задачу,
      разнесённый старт (чтобы рестарт не выстрелил всеми сборщиками разом), остановка
      по сигналу через `signal.NotifyContext` + `httpSrv.Shutdown`. Выключается
      `COLLECTOR=off` — дев-копии незачем дублировать трафик прода.
      Первым потребителем стал не майнинг, а сбор для учёта (раздел ниже).
- [ ] Кандидаты в фоновые задачи после добычи:
      - телеметрия флота (`fleet_state` → `fleet_events`) — сейчас пишется, только пока
        открыта страница флота, слепые зоны по сменам корабля;
      - снимки имущества для анализа лута (диффы по типам);
      - лунные обсерверы: отдают НАКОПЛЕННУЮ сумму без дат, динамика возможна только
        собственными снимками счётчика.
      - **накопитель для учёта ТМЦ — см. отдельный раздел ниже, это самый крупный
        потребитель планировщика.**

- [x] **Контракты раз в 5 минут.** Список кэшируется 300 с (проверено; состав —

- [x] **Вторая сборка ассетов, сохраняющая непосредственного родителя** (`collect.flatten`). `groupAssets`

### Этап 1. Ядро реестра

- [x] Таблицы `acc_doc` / `acc_place` / `acc_lot` / `acc_move` / `acc_cash`
      (`internal/store/ledger.go`). Остаток нигде не хранится: `qty_left`/`cost_left` —
      кэш поверх `acc_move`. Проводка идемпотентна по `(src, src_id)`, поэтому реестр
      можно пересобрать из `hist_*` в любой момент.
- [x] **«Провести инвентаризацию империи»** — кнопка на `/accounting`. Оказалось
      лучше задуманного: то, что куплено за собранное окно, оценивается по
      ФАКТИЧЕСКОЙ цене закупки (под FIFO на полке лежит самый свежий закуп, значит
      покупки идут с конца), остальное — по рынку с пометкой «оценка». На живых
      данных: 256 партий на 13.16 млрд по факту, 3676 на 181.55 млрд по оценке.
- [ ] Инвентаризация: экран подтверждения перед проводкой и выбор источника цены на
      строку (сейчас цена одна на всё — `average_price`, правится только пересборкой).
- [x] Покупки и продажи из транзакций, FIFO, списание без дрейфа (последний расход
      забирает весь ОСТАВШИЙСЯ `cost`). Тесты — `internal/store/ledger_test.go`, включая
      рабочий пример из §3 проекта: 1 550 млн списано, 720 млн осталось, сумма сходится.
      **Книги открываются сегодняшним числом**: сделки старше инвентаризации не
      проводятся, они уже сидят в остатках. Поэтому маржа появится с первой НОВОЙ
      продажи — зато сразу с настоящей себестоимостью.
- [x] **Разнос налога с продажи** (сбор — частично). ПРОВЕРЕНО 2026-08-24 на сыром ответе ESI: у строк
      `brokers_fee` и `transaction_tax` полей `context_id`/`context_id_type` НЕТ
      вовсе, привязки к ордеру или сделке не существует. Контекст есть только у
      `market_transaction` (id транзакции) и `contract_brokers_fee` (id контракта).
      Поэтому: налог с продажи разносить пропорционально стоимости продаж (ставка
      единая — разнос точный), а брокерский сбор матчить по ВРЕМЕНИ со значением
      `issued` ордера из `/orders/` и `/orders/history/`, сверяя сумму со ставкой ×
      стоимость ордера. Несопоставленный сбор — расход периода.
      СДЕЛАНО: налог привязан к каждой продаже точно (пара находится по ближайшему
      `id` журнала в ту же секунду — все 102 продажи выборки сошлись в пределах ±3).
      Пропорциональный разнос был бы НЕВЕРЕН: ставка у альтов разная — встретились
      4.2 %, 3.375 % и 5.025 %. Сбор сопоставляется с ордером по времени (38 из 65)
      и пока остаётся расходом периода — от сбора к конкретным единицам товара
      дороги нет, транзакция не называет ордер.
- [ ] Платежи между своими персонажами — внутренние, мимо прибылей и убытков. Иначе
      курьерка самому себе даёт и фальшивую выручку, и фальшивые затраты. Пока
      получается само собой: в реестр попадают только рыночные сделки, а журнал
      целиком не проводится — но при переходе к контрольной сумме (этап 4) это
      понадобится явно.
- [x] Отчёты: маржа по типам и склад по себестоимости — страница `/accounting`.
      ГРАБЛЯ, которая стоила первого прогона: `acc_move` и `acc_cash` нельзя джойнить
      напрямую — у продажи по движению на партию и по строке на выручку/налог, и
      джойн размножает обе стороны. Себестоимость вышла ровно вдвое больше выручки.
      Сворачивать обе таблицы ДО того, как они встретятся.
- [ ] Отчёт «оборот»: `store.Turnover` написан, но на страницу не выведен.
- [ ] Разнести брокерский сбор по типам: сейчас он период­ный расход и в разрез по
      типам не попадает вовсе (в `MarginLine.Broker` всегда 0).

- [ ] Бэкфилл: сейчас 30 дней собранных сделок пропадают для отчётов — они старше
      инвентаризации. Можно откатить сегодняшний остаток назад (остаток − покупки +
      продажи окна) и переиграть историю, получив 30 дней настоящей маржи сразу.
      Риск: за окно имущество двигали ещё производство, переработка и лут, которых
      реестр не знает, так что откат по этим типам будет врать и потребует сверки.

## AIR (`/air`, вкладка обзора империи)

ESI прогресс AIR не отдаёт вообще (эндпоинта нет, как и для Homefront), поэтому
счётчики выставляются руками плитками, а итоги месяцев живут в своей истории.

- [x] **Вкладка AIR**: все альты с портретами, 30 дневных плиток (вехи каждые 3 дня,
      финальная награда на 15-й — 75к SP альфе, +150к омеге) и 12 месячных с заливкой
      по доле дней. Клик ставит счётчик, повторный по последней — минус день.
- [x] Закрытие месяца: кнопка и автозакрытие по таймеру, синхронизированному с игровой
      шкалой («осталось 28д 1ч 2мин»); SP фиксируется в `air_month` числом на момент
      закрытия (омега — из дат аккаунта), живое состояние — `air_state`.
- [x] Автоподтяжка дней из журналов валетов: деление шкалы = запись
      `daily_goal_payouts` с reason дневного пункта (1004953); на каждый пункт две
      записи — личная и корп-дубль (в корп-журнале персонаж в `second_party_id`),
      берётся больший из двух счётчиков, не сумма. Задания дня (697xxx) и вехи (8M)
      делений не дают; накопленные пункты клеймятся пачкой одной секундой. Счётчик
      только повышается — журнал собирается не с начала времён и не у всех альтов.
      Сверка «валет: N дн.» на строке. Это закрыло идею эвристики по `unallocated_sp`.
      Важно: плитки = выполнение (шкала засчитывает сразу), валет = получение
      (запись 1004953 падает кнопкой «Получить» вместе с 10к SP) — серый бейдж
      с недобором означает в том числе «висят незабранные награды».
- [ ] **Проверить на стыке 30.09→01.10**: сгорает ли пул незабранных наград при
      обновлении шкалы (владелец подозревает, что нет). Если сгорает — фиксацию SP
      при закрытии месяца перевести с плиток (выполнено) на валет (получено).
