# EVE Empire

Личный кабинет для управления альтами EVE Online через ESI.
Цель: локальный веб-кабинет (LAN/VPN only) с деплоем в контейнер на Mikrotik RB5009 (arm64).

## Запуск (dev)

```powershell
go build -o eve-empire.exe ./cmd/server   # сборка
.\eve-empire.exe                           # http://localhost:8080
go test ./internal/pi/                     # тест формулы добычи
```

Конфиг — `.env` (в .gitignore, есть `.env.example`): EVE_CLIENT_ID/SECRET, ENCRYPTION_KEY
(64 hex = AES-256 для refresh-токенов), ESI_USER_AGENT, DB_PATH (по умолчанию
eve-empire.db), LISTEN_ADDR (:8080). **EVE_SCOPES задавать НЕ надо** — код сам знает
свой список; длинный набор ломает логин (см. грабли ESI).
Callback приложения EVE: `http://localhost:8080/callback` (developers.eveonline.com).

**Приложений EVE два, по одному на копию** (см. «Две копии»). В `.env` лежит дев,
прод — в `.env.prod` (тоже в .gitignore), и `deploy\ros-commands.ps1` кладёт его
поверх при сборке команд для роутера. Так дев-приложение физически не может уехать
на микротик. `ENCRYPTION_KEY` у обоих **общий** — иначе базы перестанут ходить
между машинами.

**Шаблоны вшиты в бинарник (embed) — после правки .html обязательна пересборка.**
Порядок именно такой: сначала УБИТЬ процесс, потом собирать. Работающий exe заблокирован,
а если новый экземпляр не займёт :8080, он тихо умрёт и старый продолжит отдавать
прежнюю сборку — правки «не работают», хотя сборка прошла. В Git Bash `pkill` тут
бесполезен, нужен `taskkill //IM eve-empire.exe //F`; он же подменяет пути в аргументах
(`-d "back=/settings"` уезжает в `C:/Program Files/Git/settings`) — для curl ставить
`MSYS_NO_PATHCONV=1`.

## Две копии

- **Дев** — `http://localhost:8080` на машине разработки, своя `eve-empire.db`.
- **Прод** — контейнер на RB5009, `http://172.20.20.1:8080/`, своя база и свой набор
  залогиненных персонажей (их там втрое больше). Скриншоты из прода локально не
  воспроизводятся — не гоняться за расхождением, а спрашивать, откуда картинка.
  Пакет для деплоя собирает `deploy\package.ps1`.

**ГРАБЛЯ, из-за которой у копий разные приложения EVE.** Refresh-токен выдаётся на
пару «приложение + персонаж», и EVE ротирует его при каждом обновлении: старый гаснет,
новый сохраняется ([client.go](internal/esi/client.go), `accessToken`). Пока обе копии
работали от одного client_id, они делили одни и те же токены — и та, что обновилась
второй, теряла доступ ко всем персонажам сразу. Развели по разным приложениям:
`http://localhost:8080/callback` у дева, `http://172.20.20.1:8080/callback` у прода.
Заодно решилась проблема единственного callback на приложение.

Следствие: **база, перенесённая с прода, приезжает с чужими токенами**. Расшифруются
они нормально (ключ общий), но обновиться не смогут — EVE ответит `invalid_grant`,
персонажей придётся авторизовать заново. Аккаунты, теги и порядок в сайдбаре при этом
переживают повторный логин: `tokens` перезаписывается по character_id, `characters`
не трогается.

Для этого есть страница **`/reauth`** ([reauth.go](internal/web/reauth.go), ссылка из
настроек): список персонажей по аккаунтам со статусом токена и одна кнопка «Войти ещё».
Статус берётся из колонки `tokens.client_id` — чьим приложением выдан токен; пусто
означает «сохранён до появления колонки», то есть после первого же деплоя этой версии
прод тоже покажет весь список неизвестными, и это нормально.

Почему одна кнопка, а не по кнопке на персонажа: **SSO не принимает, кого именно
авторизовать** — она показывает свой список персонажей того аккаунта, под которым вы
вошли. Ускорение даёт не выбор, а возврат: `/login?back=` кладёт адрес в куку
`eve_sso_back`, и колбэк возвращает на `/reauth` вместо карточки персонажа. Один
аккаунт — это вход один раз, дальше по два клика на альта. `back` пропускается через
`localPath` (только собственные пути), иначе получился бы открытый редирект.

## Ключевые механизмы

- **Stale-while-revalidate**: хендлеры берут `esiFor(r)`: обычный запрос → `StaleView()`
  (отдаёт протухший кэш мгновенно, помечает Stale), запрос с заголовком `X-Fresh: 1`
  (шлёт JS страницы) → строгий клиент с сетью. JS подменяет #main, а список персонажей —
  только если он реально изменился (см. «Переходы» ниже).
  Кэш двухуровневый: память + таблица esi_cache (переживает рестарт).
  **СЛЕДСТВИЕ 1: все обработчики событий вешать делегированием на `document`** — подмена
  `#main` убивает слушатели, навешенные на сами элементы.
  **СЛЕДСТВИЕ 2: страница, отвечающая на POST, не должна помечаться Stale.** Ревалидация
  дёргает `location.href` ЧЕРЕЗ GET, тела формы в нём нет — свежий результат через
  секунду затрётся пустой страницей. В `handleSkillPlanner` для POST передаётся `nil`
  вместо `stale`; так же поступать во всех будущих формах, отдающих результат на POST.
- **Переходы: меняется только центр.** Ссылки остаются настоящими `<a href>` (без JS,
  в новой вкладке и по прямому адресу всё работает как обычная многостраничная выдача),
  но делегированный обработчик перехватывает клик, тянет страницу целиком и подставляет
  ТОЛЬКО `#main`, правя адрес через History API. Сайдбар при этом не пересоздаётся:
  три десятка портретов не моргают, прокрутка, выделение и свёрнутые аккаунты живут
  дальше. GET-формы (настройки таблицы руд) идут тем же путём — поэтому авто-сабмит
  зовёт `requestSubmit()`, а не `submit()`: последний НЕ поднимает событие `submit`.
  **СЛЕДСТВИЕ 3: после подмены центра стреляет событие `page:swap`** — всё, что модуль
  делает не по делегированию, а один раз при загрузке (`applyBPFilter`, `syncAuto`),
  обязано на него подписаться, иначе после перехода не оживёт.
  **СЛЕДСТВИЕ 4: `innerHTML` не выполняет `<script>`** — `runPageScripts()` пересоздаёт
  теги вручную (на планетарке так приезжает `window.PI_RECIPES`).
  Ссылки альтов в сайдбаре и подсветку выставляет `markSidebar()` из `data-section` и
  `data-charid` на `<body>`; сам список сервер отдаёт один раз.
- **Сайдбар обновляется, только если данные изменились.** `syncSidebar()` сравнивает
  свежий HTML списка с текущим и трогает DOM лишь при отличии, сохраняя прокрутку.
- **Аккаунты в сайдбаре сворачиваются** в ряд из ТРЁХ портретов — столько слотов у
  аккаунта в игре; недостающие рисуются заглушками (`emptyslots` в FuncMap). Состояние
  в localStorage (`acctCollapsed`), поэтому переживает и переходы, и перезагрузку.
- **Section — это подстраница ПЕРСОНАЖА** (`charSections`), а не любая страница. Ссылки
  альтов ведут в тот же раздел, что открыт сейчас; страница настроек в набор не входит —
  иначе сайдбар вёл на несуществующий `/characters/{id}/settings` (404, так и было).
- **Привязка к аккаунту — в настройках**, полем с `datalist` существующих аккаунтов.
  Раньше единственным способом было перетаскивание карточки в сайдбаре — догадаться
  об этом было нельзя. Перетаскивание осталось для порядка внутри списка.
- **Токены**: access обновляется за минуту до истечения; refresh-токены ротируются CCP —
  всегда сохраняем новый. Хранение только шифрованным (AES-GCM).
- **Даты в SQLite — только unix integer** (драйвер отдаёт TIMESTAMP строками).
- **Локализация**: язык в `app_settings`, клиент дописывает `?language=` ко всем GET,
  язык входит в кэш-ключ. Настройка — /settings.
- **Линии производства**: скиллы 3387/24625 (произв.), 3406/24624 (наука),
  45748/45749 (реакции); слот занят при status active/paused/ready; корп-джобы
  занимают слоты установившего персонажа.

## Статическая база sde.db (~250 МБ, в git не кладём)

```powershell
go build -o sdeimport.exe ./cmd/sdeimport
.\sdeimport.exe -db sde.db -workers 48   # возобновляемый: повтор докачает недостающее
.\sdeimport.exe -db sde.db -redata       # переимпорт данных без иконок
```

Источник — официальный JSONL-SDE (`developers.eveonline.com/static-data/tranquility/`:
`latest.jsonl` → buildNumber → `eve-online-static-data-<build>-jsonl.zip`, ~99 МБ).
Содержимое: 52 822 типа (ru+en имена/описания), 1610 групп, 645 744 dogma-атрибута,
12 379 требований навыков (`type_skills`), 5082 чертежа, 68 планетарных схем,
19 880 иконок 64px + 4896 иконок копий чертежей — всё BLOB-ами.
Плюс для таблицы руд: `type_materials` (47 051 строка, 9541 тип — что даёт переработка
ПАРТИИ в `portion_size` штук), `type_materials_rand` (24 строки — руды со случайным
составом), `compressible` (212 связей сырьё → компресснутый тип) и колонка
`types.variation_parent_id`. **Появились позже основной базы: если в sde.db их нет,
нужен `-redata`** (страница руд честно об этом скажет).

- **Иконки чертежей** — вариант `bp`, НЕ `icon` (у чертежей `icon` отдаёт 400).
  Порядок перебора: `icon → bp → render`. Копии (BPC) — вариант `bpc`, таблица
  `icons_bpc`, отдаётся как `/icons/{id}?bpc=1`.
- Без иконок ~7100 типов, из них 7077 — SKIN'ы (их нет на CDN).
- Атрибуты имплантов: 175 харизма, 176 интеллект, 177 память, 178 восприятие,
  179 сила воли, 331 номер слота.
- Связи «тип планеты → сырьё P0» в новом SDE НЕТ — таблица `rawByPlanet` захардкожена
  в internal/sde (стабильна годами).
- Сервер работает и без sde.db (с предупреждением, часть данных недоступна).

## Грабли ESI (проверено болью)

- **Не проси «все scopes».** Полный список EVE — 72 разрешения, 2.4 КБ текста; с ним
  `login.eveonline.com` отвечает «request too long» и логин не проходит вообще (лечится
  не бубном с отдельным окном, а укорачиванием списка). `defaultScopes` в
  `internal/config` — ровно то, что кабинет вызывает: 31 штука, authorize-URL 1.2 КБ.
  Добавляешь новый вызов ESI — добавь туда его scope. Переменная `EVE_SCOPES`
  перекрывает этот список: если она задана длинным набором, всё сломается снова.

- `/universe/names/` **не резолвит структуры (id ≥ 1e12) и планеты** — и валит весь
  батч. Структуры → авторизованный `/universe/structures/{id}/`, планеты →
  `/universe/planets/{id}/`. Батчи names ≤ 1000 id.
- Батч `/universe/names/` всегда отдаёт английский. Локализованные имена типов —
  только `/universe/types/{id}/` (см. `typeNamesLocalized`).
- **Corporation Projects**: только `https://esi.evetech.net` (без /latest!) с заголовком
  `X-Compatibility-Date`. `state=` принимает ТОЛЬКО `All|Active`. Листинг курсорный
  по 10, старые первыми — ходить по `cursor.after`.
- «Работы на паузе на цитадели» = corp industry jobs `status=paused`, это НЕ Projects.
- Автоимена кораблей — Python-repr `u'Capsule\xa0— Имя'` → декодер `cleanPyString`.
- Принадлежность персонажа к аккаунту ESI не раскрывает — группы/теги ручные.
- **Корпоративных НБ, EverMarks и плекс-хранилища в API нет вовсе.** Личные LP —
  `/characters/{id}/loyalty/points/`; личные EverMarks = LP корпорации «Paragon».
- **Планетаркой нельзя управлять**: `esi-planets.manage_planets.v1` даёт только GET.
  Во всём ESI запись есть лишь для контактов, почты, флотов, фиттингов, имён ассетов.
- **Статуса завода в ESI НЕТ.** Поля пина: `pin_id, type_id, schematic_id, latitude,
  longitude, install_time, expiry_time, last_cycle_start, contents` (+`extractor_details`
  у буров). Ни `is_active`, ни остатка цикла. **ESI пересчитывает колонию лениво**, и
  `last_cycle_start` врёт в ОБЕ стороны — сверено 2026-08-03: у работающих заводов одного альта
  (планета V, бур переставлен в тот же день) он показывал 21.12.2024, у стоящих заводов
  у другого (планета I той же системы, сырья в колонии нет) — «8 минут назад». Правка колонии его вперёд
  тоже не двигает: `last_update` колонии = сегодня, даты пинов — декабрьские. `contents`
  заводов — часть того же снимка, тоже может быть протухшим. Простой определять по ним
  НЕЛЬЗЯ, только по цепочке поставок.
- **Флот — единственная большая запись в ESI** (14 маршрутов, `esi-fleets.read_fleet.v1`
  и `write_fleet.v1`). Проверено на живом флоте 2026-08-04:
  - **всё, кроме `/characters/{id}/fleet/`, доступно ТОЛЬКО текущему боссу флота**;
    вингкому и рядовым ESI отвечает 404 «The fleet does not exist or you don't have
    access to it!». Роль во флоте не даёт ничего.
  - создать/распустить флот, дать рекламу в Fleet Finder, броадкасты, флотский варп,
    «готовность» — **в API нет вовсе**. Только управление уже созданным флотом.
  - имя эскадры/эскадрильи — **максимум 10 СИМВОЛОВ** (не байт: «Эскадрилья» = 10 симв.
    /20 байт проходит, «01234567890» — нет). Дефолтные имена приходят локализованными
    (`?language=`) и ДЛИННЕЕ лимита («Эскадрилья №2» = 13) — то есть после
    переименования вернуть дефолт нельзя. Лечится только `DELETE` + `POST` пустой
    эскадрильи: новая снова получает дефолтное локализованное имя.
  - удалять можно только пустые эскадры/эскадрильи; приглашение персонажа с CSPA-сбором
    ESI не пропускает (422).
  - `wing_id`/`squad_id` = −1 там, где неприменимо (ФК; командир эскадры вне эскадрильи).
  - кэш чтений 5 с, `/characters/{id}/fleet/` — 60 с; поэтому весь пакет флота ходит
    мимо нашего кэша (`Client.call`, см. ниже).
- **Добыча**: `/characters/{id}/mining/` (`esi-industry.read_character_mining.v1`,
  кэш 600 с, постранично) — единственное место в ESI, где выработка отдаётся прямо.
  Гранулярность: день × система × тип руды, БЕЗ времени и без объёма/ISK. Документация
  обещает 30 дней, по факту 2026-08-04 отдавалось с 18.06 (47 дней) — окно шире
  документированного, но конечное: **историю надо копить у себя**.
  Корпоративные луны — `/corporation/{id}/mining/observers/` (+ `/{observer_id}/`) и
  `/corporation/{id}/mining/extractions/`. **ГРАБЛЯ: путь `/corporation/` в единственном
  числе**, в отличие от всех прочих корп-маршрутов; нужна роль Accountant/Director,
  иначе 403 «Character does not have required role(s)». У нас обсерверов нет (луны не
  качаем), в NPC-корпе — 403.
- **Почта**: `/characters/{id}/mail/` — 50 заголовков за запрос, глубже — только
  курсором `last_mail_id` (отдаёт письма СТАРШЕ указанного id); окно не режется,
  достаётся вся история (проверено до 2015). Тело — `/mail/{mail_id}/` (кэш 30 дней),
  формат игровой разметки как у описаний типов — чистится тем же `sde.DescriptionHTML`.
  ГРАБЛЯ: id рассылок (recipient_type=mailing_list) НЕЛЬЗЯ класть в батч
  `/universe/names/` — валят весь батч; их имена только в `/mail/lists/`.
  Чтение через ESI письмо прочитанным НЕ помечает (это PUT, мы не пишем).
- **Структуры корпорации**: `/corporations/{id}/structures/` — топливо (`fuel_expires`,
  отсутствует = low power), состояние (`shield_vulnerable` — норма, `armor_reinforce`/
  `hull_reinforce` — под атакой) с таймерами, сервисы, окно реинфорса. Нужна роль
  **Station Manager**, причём подойдёт любой альт корпорации — страница перебирает всех.
  **Атака на структуру видна ТОЛЬКО в личных уведомлениях**
  (`/characters/{id}/notifications/`, кэш 600 с): StructureUnderAttack /
  StructureLostShields / StructureLostArmor / StructureFuelAlert и т.п. `text` —
  YAML-блоб; ГРАБЛЯ: `charID` в нём — агрессор только у атакующих типов, у
  StructureItemsDelivered это курьер. Уведомления живут у ESI годами (нашлись
  OwnershipTransferred 2015 года), одинаковые события приходят каждому альту корпы —
  дубли клеить по (тип, время, structureID).
- **Лута в ESI нет вовсе.** Ни подобранного с врэков, ни сальважа. Косвенные источники:
  снимки `/characters/{id}/assets/` с диффом по типам (у нас ~4.5k строк на всех — снимок
  дешёвый), журнал кошелька (`bounty_prizes`, `corporate_reward_payout`,
  `agent_mission_reward`, `daily_goal_payouts`) и транзакции продаж. Килмейлы дают
  выпавшее на кил, а не подобранное.
- Сырой ответ ESI для отладки лежит в рабочей БД: `SELECT body FROM esi_cache WHERE url
  LIKE '%planets/40443776%'` (тело — как пришло, ключ включает `?language=`).
- Обязателен User-Agent с контактом; уважать заголовок Expires (наш кэш это делает).

## Цены

`/markets/prices/` — 1 запрос, ~16k типов, кэш ~1 ч: `average_price` = «оценочная
стоимость» из клиента (сверено: подсистема Loki 38.37M против 38.4M в игре),
`adjusted_price` — основа расчёта стоимости промышленных работ.
Реальные цены — региональные ордера: The Forge = 406 страниц, ~30 с в 16 потоков,
93 МБ raw / ~10 МБ gzip, кэш 5 мин. **Постранично весь регион качать не надо**: тот же
маршрут с `?type_id=` отдаёт книгу одного типа одной страницей — 280 типов таблицы руд
собираются за 2.5 с в 16 потоков (`esi.RegionOrderBook`), дальше живут в `esi_cache`.
`esi.RegionOrderStats` сводит книгу к шести числам: `smin/sp98/sp90` и `bmax/bp98/bp90`.
Перцентиль — **обрезка по ОБЪЁМУ**: 98-й отбрасывает 2 % самого дешёвого объёма продажи
(и 2 % самого дорогого объёма скупки) и только потом берёт крайнюю цену; одиночный
ордер на единицу такую цену уже не двигает. ОБРАТНАЯ СТОРОНА: если почти весь объём
скупки висит одним ордером по 1 ISK (инжекторы, экстракторы), обрезанные перцентили
честно садятся на него — в вотчлисте поэтому в шапке стоит `bmax`, а не перцентиль.
**PLEX не торгуется в регионах вообще**: его книга и история лежат в псевдорегионе
`19000001` (`esi.RegionPLEX`), у The Forge по нему пустой ответ.
Сторонние агрегаторы (Fuzzwork market, evemarketer, Adam4EVE) на 2026-08 не отвечают.

## Формулы EVE (сверены с клиентом до единицы)

- **Материалы чертежа**: `max(runs, ceil(base × runs × (1−ME/100) × бонус_структуры))`.
  Пример: Crucifier BP при ME10/TE20 → 21 600 Tritanium, 4 050 Pyerite, 1 688 Mexallon,
  338 Isogen, 01:20:00.
  **ПОРЯДОК ВАЖЕН, сверено с клиентом 2026-08-06** на Hydrogen Fuel Block BP, 6618 прогонов,
  ME 10, Azbel (материалы ×0.99) — все девять материалов сошлись ДО ЕДИНИЦЫ: бонус корпуса
  идёт ОТДЕЛЬНЫМ множителем после ME, округление **одно и в самом конце**, а пол «не ниже
  прогонов» — самым последним. Именно поэтому игра просит 6 618 Robotics там, где
  арифметика даёт 5 897 (`1 × 6618 × 0.9 × 0.99`).
  **У реакций ME и TE чертежа не действуют вовсе**, бонуса корпуса на материалы у них тоже
  нет — расход двигают только риги структуры (они не смоделированы).
- **Бонусы структуры — из SDE**, атрибуты корпуса: **2600** `strEngMatBonus`, **2601**
  `strEngCostBonus`, **2602** `strEngTimeBonus`, **2721** `strReactionTimeMultiplier`.
  Это МНОЖИТЕЛИ, а не проценты: Raitaru 0.99/0.97/0.85, Azbel 0.99/0.96/0.8,
  Sotiyo 0.99/0.95/0.7, у «Мороу»/«Драккус»/«Горизонт» Фортизаров только cost и time,
  Tatara — 0.75 на время РЕАКЦИЙ (у Athanor этого атрибута нет вовсе = 1).
  **ГРАБЛЯ: `strEngCostBonus` (2601) к сбору за установку НЕ применяется.** Сверка на том же
  проекте: сбор игры 172 806 123 при EIV 2 839 405 267 = 6.086 %, что равно
  `индекс 2.09 + налог 2.5 + SCC 1.5`; с множителем 0.96 вышло бы 170.6M — мимо на 1.3 %.
- **Стоимость установки работы**: `EIV × (индекс системы + налог структуры + сбор SCC 1.5 %)`,
  где EIV — **БАЗОВЫЕ** количества материалов (без ME!) в ценах `adjusted_price` из
  `/markets/prices/`. ME режет расход, но не сбор. Индексы систем — публичный
  `/industry/systems/` (`esi.IndustrySystems`, доля 0.1706 → 17.06 %), имя системы → id
  через `/universe/ids/`. ГРАБЛЯ: индекс manufacturing в Жите — 17 %, поэтому «Jita» как
  дефолтная система сборки врёт по-крупному; система по умолчанию не задана вовсе.
- **Время работы**: `base × runs × (1−TE/100) × навыки × бонус_структуры`, где `Industry`
  (3380) даёт −4 % за уровень и `Advanced Industry` (3388) −3 % за уровень (множители
  перемножаются). Сверено до секунды: `900 × 6618 × 0.8 × 0.68 × 0.8 = 2 592 138 с`, и
  клиент показывает ровно **30D 00:02:18**.
- **ГРАБЛЯ: `max_production_limit` — это лимит прогонов КОПИИ, а не производственной
  работы.** Ограничение прогонов по нему резало 6618 прогонов топливных блоков до 200;
  в расчёте оно теперь только справка под полем «Прогонов».
- **«Примерная цена за всё» в окне проекта** = `Σ average_price × количество`
  (сверено до ISK: 3 983 112 148), **объём** = `Σ types.volume × количество`
  (1 779 590.0 м³ — совпало точно).
- **Программа добычи экстрактора** (`pi.ExtractionProgram`, тест
  `internal/pi/extraction_test.go`):
  ```
  t      = (i + 0.5) × cycle/900
  decay  = base / (1 + t × 0.012)
  wobble = max(0, (cos(ph + t/12) + cos(ph/2 + t/5) + cos(t/2)) / 3),  ph = base^0.7
  qty    = floor(decay × (1 + 0.8 × wobble) × cycle/900)
  ```
  ДВА НЕОЧЕВИДНЫХ МОМЕНТА: (1) множитель `cycle/900` — `qty_per_cycle` из ESI это
  выработка за 15-минутную единицу, НЕ за цикл; (2) **шум только прибавляет** —
  community-формулы применяют его со знаком и занижают половину циклов.
  Сверка: base 13848, цикл 4 ч, 84 цикла → 15 контрольных точек и итог 3 680 687.
- **Потребности планетарки**: `циклы = ceil(нужно / выход_за_цикл)`, вход = циклы × qty.

**Карточка «Планеты» на Обзоре** — 6 плиток (потолок игры): колонии, затем свободные
слоты, затем закрытые. Сколько открыто — `1 + уровень навыка 2495` («Параллельное
управление наземными базами»); закрытые рисуются штриховкой с замком. Иконка планеты —
из sde по `planet_type` (`sde.PlanetTypeID`: Temperate 11, Ice 12, Gas 13, Oceanic 2014,
Lava 2015, Barren 2016, Storm 2017, Plasma 2063). Вокруг иконки ТРИ кольца, снаружи внутрь:
- склады (без КЦ) — доля занятого объёма. Кольцо собрано из 12 цветных дуг
  (`storageRing`/`loadColor`): цвет привязан к УГЛУ, а не к остатку, поэтому наполовину
  забитая колония читается как зелёно-жёлтая, а красной становится только полная.
  ГРАБЛЯ: обычный `linearGradient` вдоль bbox красит 55 % уже в красный — не годится.
- производство (оранжевое) и добыча (синее) — прогресс ближайшего к завершению цикла,
  живая перерисовка тем же `tickRings` (селектор `.parc[data-cycle-end]`, длина кольца
  в `data-len`). Нет буров/заводов — белое кольцо, есть и стоят — пульсация по всему кольцу.
Подсказка при наведении собирается на сервере в скрытый `.ptip-src` внутри плитки, JS
копирует его в общий `#pintip` (в подсказке — буры, заводы, склады и «к переработке»:
запас каждого входного материала и на сколько циклов его хватает, `colonyFeed`).
Данные для карточки и для вкладки «Планеты» готовит общий `colonyViews`.

**Вкладка «Планеты» персонажа** (`/characters/{id}/planets`) — мониторинг его колоний:
- схема колонии в игровом стиле: круглые пины (жёлтый завод, синий космопорт,
  бирюзовый экстрактор, фиолетовый КЦ), иконка продукта в центре, белое кольцо =
  прогресс цикла, простаивающие пульсируют. Раскладка СХЕМАТИЧНАЯ (`layoutColony`):
  КЦ слева вверху столбиком, экстракторы справа СТОЛБИКОМ (строкой наезжали на кольца
  заводов на узкой карте), космопорты в центре, заводы кольцами.
  Геометрия считается в логических 760×507 px при пине 46 px и зазоре 10 px, а блок
  МАСШТАБИРУЕТСЯ под колонку: `aspect-ratio: 760/507`, `container-type: inline-size`,
  всё внутри в `cqw` (пин 6.05cqw, иконка 2.9cqw, кольца box-shadow .39/.79cqw).
  Ширина колонок фиксированной долей (45 %/55 %), НЕ «сколько осталось» — иначе ширина
  карты зависит от длины подписей под графиками и колонии на одной странице получают
  разный масштаб. В стопке (≤1250 px) flex-basis сбрасывается: он лёг бы на высоту.
- стрелки = **маршруты** (`routes`), по одной прямой `source → destination`, waypoints
  игнорируются. Пунктир бирюзовый = сырьё на фабрику, зелёный сплошной = продукция;
  тип по получателю маршрута. ГРАБЛЯ: `content_type_id` маршрутов надо класть в батч
  резолва имён, иначе транзитные товары без подписи.
- подсказка при наведении (`#pintip`, мгновенная): продукт, входы за цикл, длительность,
  содержимое, остаток цикла; заодно подсвечиваются потоки этой структуры.
- экстракторы справа от схемы: столбчатая диаграмма программы (столбец = цикл, подсказка
  «цикл N · объём · дата»), статы (цикл / за цикл / в час / до конца цикла / программы),
  под графиком белый прогресс-бар текущего цикла (`.extrcyc`, тот же тикер `tickRings`,
  что крутит кольца пинов). Наведение на пин бура подсвечивает его карточку
  (`.extr[data-extr]` ↔ `.pin[data-pin]`, класс `.hot`) — иначе при нескольких бурах
  непонятно, какой график чей.
  График с запасом сверху (`chartTop` 14 ед. из 100) + 4 пунктирные линии 25/50/75/100 %
  от пика с подписями (`.gridlab`, позиционируются в % от `.extrwrap` — поэтому у обёртки
  ровно та же высота, что у svg). Штрихи и толщина линий — `vector-effect="non-scaling-stroke"`,
  иначе `preserveAspectRatio="none"` их растягивает.
- хранилища гридом: занятость = `contents × types.volume / types.capacity`
  (Launchpad 10000 м³, Storage 12000 м³, Command Center 500 м³), пороги 70/90 %.
- **простой фабрики — по маршрутам И количеству**: вход обеспечен, если завод держит
  полный цикл сырья, либо маршрут тянет его из живого экстрактора / РАБОТАЮЩЕГО завода /
  склада с запасом ≥ цикла / пина, который сам транзитом это получает (рекурсия по
  маршрутам, множество работающих растёт до фикс-точки). ГРАБЛЯ: старая проверка «материал
  есть где-то в колонии в любом количестве» врала — завод с 5 единицами из нужных 10 при
  вставших поставщиках показывался работающим. ВТОРАЯ ГРАБЛЯ: живой бур считается
  поставщиком только после первого ЗАВЕРШЁННОГО цикла (`Delivered`) — выдача идёт в конце
  цикла, и свежепоставленная программа ещё ничего не положила; если в космопорте лежит
  другое сырьё, заводы стоят и ждут.
- **жёлтая черта на графике бура** (`markExtractorCoverage`): момент, с которого добычи
  не хватает заводам. Спрос = сумма входов всех заводов колонии по этому сырью в ед./сек;
  сравниваются НАКОПИТЕЛЬНЫЕ итоги (запас жирных первых циклов покрывает провал поздних).
  Буры на одном сырье считаются ВМЕСТЕ (общий склад) на общей оси времени — момент один,
  на графики проецируется каждому в свой номер цикла. Отсчёт стартует после первого полного
  цикла самого позднего бура, иначе на первых секундах вылезает фантомный дефицит.
  Упрощения: текущие остатки на складах в буфер не берутся, заводы считаются работающими
  непрерывно (спрос — верхняя оценка), деление добычи между заводами не моделируется.

**Обзор империи — вкладки** (`{{define "empiretabs"}}` в layout.html, аргумент = ключ
активной вкладки): «Сводка» (`/`), «Кошельки» (`/wallets`), «Обучение» (`/training`),
«Производство» (`/industry`), «Планеты» (`/planets`), «Добыча» (`/mining`),
«Структуры» (`/structures`).
Разные URL, а не панели на одной странице: иначе `/` тянул бы данные всех вкладок сразу.
Сводка — компактные карточки, у каждой в заголовке
ссылка «подробно →» на свою вкладку.

- *Сводка · кошельки*: список — это САМИ итоги. Строки «Персонажи всего» и «Корпорации
  всего» (`.wgrp[data-wtoggle]`) кликом разворачивают под собой своих участников
  (`.wsub[data-wgroup]`), внизу общий баланс. Персонажи внутри — по убыванию баланса.
- *Сводка · обучение*: квадратики уровней + навык + обратный отсчёт, **сортировка от
  ближайшего завершения к дальнему**, альты без очереди в конце. Таблица `.trtab` —
  `table-layout: fixed` с прибитыми колонками: отсчёт (`.tmc`) и уровень (`.lvc`) не
  переносятся, и при авто-раскладке «10д 6ч 54м 22с» выталкивал таблицу за край карточки.
  Уровень — ОТДЕЛЬНАЯ колонка: внутри ячейки имени его съедало многоточие ровно на
  длинных названиях.
- *Сводка · линии*: та же таблица + строка «Всего».
- *Сводка · омега*: строка на аккаунт **в порядке сайдбара** (список визуально
  совпадает с ним один в один, аккаунты без дат — прочерками), три колонки с датой
  и остатком; «изменить →» ведёт в настройки.

**Омега и учебные места** (`internal/web/omega.go` + таблица `account_omega`):
даты окончания омеги и двух доп. учебных мест (сертификаты MCT; больше двух у
аккаунта не бывает — три обучающихся пилота это потолок игры). ESI статус подписки
НЕ отдаёт ничем, даты вводятся руками в настройках из окна «Учётная запись» клиента,
EVE-время (UTC). Формат ввода как в игре — `2027.03.01 05:20` или `2026.11.29`;
дата без времени действует до конца своего дня (иначе «истекает 29-го» краснело бы
утром 29-го). Хранится текстом `YYYY-MM-DD[ HH:MM]` с ключом = меткой аккаунта;
таблица НАРОЧНО отдельная от `account_order` — ту перетаскивание в сайдбаре
пересоздаёт через DELETE+INSERT, и колонка в ней погибла бы при первой сортировке.
Все три даты пустые = строка удаляется. В заголовке группы сайдбара бейдж `Ω 91д`
по ближайшей из заполненных дат: оранжевый ≤ 14 дней, красный ≤ 7 или если что-то
уже истекло (`Ω истекла`); наведение показывает все даты. Косвенная сверка на
будущее: когда омега реально кончается, у альтов встаёт очередь навыков — её
приложение уже читает.

**Квадратики уровней навыка** — шаблонная функция `squares <изучено> <цель>`: белые до
изучённого уровня, бирюзовые до целевого, текущий мигает (селектор анимации перечисляет
контейнеры: `.qrow.qactive`, `.trrow.qactive`, `.char .trq`, `.trainrow`). Один вид в
сайдбаре, на «Навыках», в сводке и на вкладке «Обучение» — не рисовать их вручную.

**Вкладка «Кошельки»** (`/wallets`) — «шапки» из игры: карточка на каждого персонажа
(ISK, число корпораций с НБ, EverMarks) и на каждую корпорацию (ISK всего + счета,
у которых баланс ненулевой; единственный счёт не показываем — он повторяет итог).
Вертикального меню тут НЕТ: переключателем работают сами плитки итогов
(`.pstat.pick[data-wfilter]`, выделение рамкой у `.active`) — «Общий баланс» по
умолчанию показывает обе группы `[data-wsection]`, «Персонажи» и «Корпорации»
оставляют свою. Плитка «Плексы» некликабельна — это не фильтр.

ГРАБЛЯ СЕТКИ: у вкладки «Обучение» своя сетка (`.trgrid`, три колонки `minmax(0,1fr)`,
2 при ≤1250 px, 1 при ≤900 px), а НЕ общий `.cardgrid` — у того `max-width: 1400px`,
и на широком окне справа оставалась мёртвая полоса, пока шапка со статистикой
тянулась во всю ширину.

**Вкладка «Обучение»** (`/training`) — карточка на альта со **следующими 5 навыками**
очереди в том же виде, что план на странице «Навыки» (`.qrow` + квадратики), плюс общее
время плана, дата конца и сколько записей осталось за кадром. Очередь готовит общий
`buildQueue(sheet, queue, now)` — им же живёт страница «Навыки».

**Вкладка «Производство»** (`/industry`) — ОДИН общий список работ всех персонажей
(`.jobs`, ближайшие сроки сверху), 8 колонок: персонаж-установщик (+бейдж «корп»),
его занято/всего линий **этого же типа**, чертёж, тип работы, прогоны, локация
(`facility_name`), остаток, стоимость запуска. Клик по строке — та же модалка деталей
(`data-job`). Сверху три кнопки-плитки Производство / Наука / Реакции
(`.pstat.pick[data-jfilter]`) с загрузкой линий: клик оставляет работы только своего
типа, повторный клик по активной снимает фильтр (по умолчанию видно всё).
- ГРАБЛЯ: `table-layout: fixed` и ширины ВСЕХ колонок в процентах (в сумме 100).
  При авто-раскладке таблица прыгала на каждом переключении фильтра — ширины считались
  по уцелевшим строкам; при пиксельных ширинах весь остаток доставался колонке чертежа,
  и на 1200 px она схлопывалась до иконки. Ячейки режутся многоточием, полный текст —
  в `title`.
- ГРАБЛЯ: в модалку джоба нельзя проваливаться кликом по ссылке или чипу предмета внутри
  строки — обработчик `tr[data-job]` пропускает клики по `a, .itm[data-type]`, иначе
  поверх карточки предмета открывается вторая модалка.

**Вкладка «Планеты» империи** (`/planets`) — сводка по колониям ВСЕХ персонажей.
- **Шапка, общая для обеих секций**: плитки Колонии / Буры / Заводы / Добыча в час
  (`.phead` + `.pheadstats` + `.pstat`) и под ними добыча в час по сырью чипами
  (`.pheadyield`, в title чипа — число буров).
- **Вертикальное меню слева** (`.vwrap` + `.vnav` + `.vbody`, панели переключаются
  делегированным обработчиком по `data-vpane` / `data-vpane-body`), два пункта со
  счётчиками: «Требует внимания» и «Планеты персонажей».
- *Требует внимания* (`slotAlerts`) — только то, по чему надо действовать: завершённая
  или истекающая (<24 ч) программа бура, стоящие заводы (все / часть), склады ≥70 и ≥90 %,
  момент, с которого добычи перестанет хватать (`CoverCycle`). Красный маркер — уже стоит,
  жёлтый — встанет скоро. **Одна строка на колонию** (`colonyAlert`): все её проблемы
  склеиваются через «и» в одной ячейке, примечания — через «·» в том же порядке; маркер
  строки = худшая из них, но каждый кусок текста красится своей срочностью. Строки со
  стоящим — первыми. Не разносить проблемы одной колонии по строкам, владельцу нужна
  именно склейка.
  ГРАБЛЯ ПАЛИТРЫ: глобальный `.err` — ЯНТАРНЫЙ, а `.lvl` — синий с разрядкой (уровень
  навыка), для срочности не годятся; на этой странице цвет берут `.sev-err` (красный,
  как маркер) и `.sev-warn` (янтарный).
- *Планеты персонажей* — те же плитки планет, что на Обзоре персонажа.
Данные собирает `handleEmpirePlanets`: по каждому персонажу параллельно `colonyViews`
+ `Skills` (для числа открытых слотов), дальше общий `planetSlots`. Всё из кэша ~0.25 с,
с принудительным обновлением (`X-Fresh: 1`) ~1.4 с.
Плитка планеты вынесена в `{{define "planettile"}}` в layout.html и переиспользуется
Обзором и этой страницей; поэтому у `planetSlot` есть собственное поле `Now` — внутри
`{{template}}` до данных страницы не дотянуться.

**Инструменты → Планетарная промышленность** (`/tools/planetary`), три вкладки:
1. *Схема производства* — аналог eve-webtools.com/Planetary: 5 колонок P0→P4
   (15/15/24/21/8) + 8 типов планет, цены, поиск. Клик красит цепочку и рисует SVG-связи.
2. *Расчёт потребностей* — целевые товары → разложение по тирам до сырья, сводка
   «сырьё по рынку / цель по рынку / наценка». Рецепты уходят в браузер одним JSON
   (`sde.PIRecipes` → `window.PI_RECIPES`).
3. *Шаблоны заводов* — хранилище колоний (`pi_templates`), импорт/экспорт формата игры,
   генератор.

**Вкладка «Добыча»** (`/mining`) — свод по руде, две панели `.vnav`:
- *Персонажи* — личные леджеры всех альтов (`/characters/{id}/mining/`): график по дням
  (столбец = сутки, стек по персонажам, цвет закреплён за альтом и повторяется в таблицах;
  пунктирные линии пика и половины пика лежат в одном боксе с колонками, поэтому подписи
  действительно отмечают масштаб), таблицы по персонажам, рудам и системам. Ось
  непрерывная от первого дня истории до сегодня — простои читаются как провалы; если
  история длиннее 120 дней, начало обрезается.
  **ТРИ РАЗРЕЗА одних и тех же дней** — ISK (по умолчанию), объём, количество; плитки
  итогов и есть переключатель (`.pstat.pick[data-mfilter]` → `[data-mchart]`), выбранный
  разрез запоминается в URL (`?m=`), иначе клик по дню его сбрасывал бы.
  **Клик по столбцу** (`.mcol[data-day]`) фильтрует ВСЕ списки ниже по этому дню
  (`?day=YYYY-MM-DD`), повторный клик по выбранному — снимает фильтр. Агрегация вынесена
  в `miningCtx.aggregate` и гоняется дважды: по всей истории (график, итоги, ЦВЕТА
  персонажей) и по выбранному дню (таблицы). Цвета берутся из первого прохода — иначе
  пилот менял бы цвет при выборе дня. Пустые дни некликабельны.
  Считать добычу В ЕДИНИЦАХ НЕЛЬЗЯ: механики разные — единица Veldspar это 0.1 м³ и
  копейки, единица Glacial Mass — 1000 м³ и ~150k ISK, лёд идёт по одному за цикл.
  У владельца лёд — 0.14 % единиц и 78 % стоимости; по количеству топ-дни 15–17.07,
  по ISK — 18.06 и 02–04.07, картина другая целиком.
  **Цена — средняя по Жите (The Forge, регион 10000002) ЗА ТОТ ДЕНЬ**, когда добыто
  (`esi.JitaHistory` → `/markets/{region}/history/`, ~396 дней, публичный, кэш до суточной
  прокрутки). История отстаёт на день-два, поэтому `PriceSeries.At` берёт последнюю
  известную цену НЕ ПОЗЖЕ нужного дня, дальше — фолбэк на `average_price`.
  Цена пишется в базу рядом с количеством (`mining_ledger`), прошлые дни задним числом
  не переоцениваются; нулевая цена никогда не затирает уже известную (сегодняшние строки
  приходят без цены и получают её на следующем проходе). Леджер ESI (~30 дней) при каждом
  заходе апсертится в `mining_ledger`, а страница рисуется УЖЕ ИЗ БАЗЫ — история копится
  сама, пока заходишь на страницу. Объём — из sde (`Volumes`).
- *Луны* — по каждой корпорации: обсерверы (`/corporation/{id}/mining/observers/`) с
  разбивкой «пилот × руда» и экстракции с таймерами. Корпорации без обсерверов со
  страницы НЕ убираются: видно, что проверены. У NPC-корпы честный отказ по ролям.
Имена руд берём из sde (локализованные), `/universe/names/` для них отдаёт английский.
ГРАБЛЯ: id лун нельзя класть в батч `/universe/names/` (как планеты и структуры) —
`esi.MoonName` ходит в `/universe/moons/{id}/`.
Обсервер отдаёт НАКОПЛЕННУЮ сумму без дат — динамика по лунам возможна только своими
снимками счётчика; личный леджер уже суточный, но его окно конечное.

**Вкладка «Структуры»** (`/structures`, `internal/web/structures.go`) — сводка по
структурам всех корпораций. Шапка: всего структур / топливо до ближайшего истечения /
в реинфорсе / боевых событий за 7 дней. Две панели `.vnav`:
- *Структуры* — таблица на корпорацию: тип чипом, имя, система, состояние
  (словарь `structStates`, готовые css-классы `pos`/`sev-warn`/`sev-err` кладёт Go,
  а не шаблон), топливо (осталось + дата, err <48 ч, warn <7 дней, «нет топлива
  (low power)» при пустом `fuel_expires`), сервисы (зелёные/янтарные), окно реинфорса
  («18:00 ±2ч», с датой смены если запрошена). Роль Station Manager ищется перебором
  всех альтов корпорации; отказ пишется честной строкой.
- *События* — уведомления всех альтов, отфильтрованные по `Structure*` +
  OwnershipTransferred, дубли между альтами склеены; для атак — проценты щит/броня/
  корпус и имя агрессора. Имя структуры берётся из списка структур, чужие/убитые —
  разовый `LocationNames`, дальше фолбэк «Структура id».


**Навыки** (`/characters/{id}/skills`) — каталог слева, план обучения справа.
В каталоге видно НЕ ТОЛЬКО изученное: уровни, которые стоят в очереди, красятся
бирюзовым (класс `q`, как в плане), строка помечается `.inq`, а на кнопке группы
висит счётчик «сколько отсюда в очереди» — иначе по дереву непонятно, что учится.
Скорость обучения (`СП/мин`) считается по паре атрибутов навыка (dogma 180/181) и
атрибутам персонажа: ESI отдаёт их УЖЕ с имплантами, доливать ничего не надо.
Показывается в строках плана, у общего времени и в каталоге у тех навыков, что стоят
в очереди — на все 400 строк это был бы шум.

**Инструменты → Таблица руд** (`/tools/ore`) — своя копия ore.cerlestes.de. Четыре
вкладки одним хендлером: руда, лёд, лунная руда, газ (`?t=`). Всё состояние в адресной
строке (`?a=` количество, `?y=` выход переработки, `?p=` статистика цены, тумблеры
`v/c/b/f`, сортировка `s/d`) — работают «назад» и ссылка на конкретный вид; настройки
формы сабмитятся делегированным `change` на `form.oreset`.

- **Выход переработки — по навыкам выбранного альта.** Кто и где перерабатывает,
  настраивается в отдельном окне (кнопка «Переработка» → `#refwin`, POST
  `/tools/ore/refinery`). Настройка живёт в `app_settings`, а НЕ в адресной строке: это
  постоянный ответ на вопрос «как я перерабатываю», в отличие от вида таблицы.
  **Наборов ТРИ — руда, лёд, лунная** (`refine_<kind>_char/struct/rig/sec`), окно правит
  набор своей вкладки, галка «применить ко всем» пишет во все три. Старые общие ключи
  (`refine_char` и т.д.) читаются как фолбэк, чтобы настройка не слетела.
  ВАЖНО: сама игра выход по видам НЕ различает — у сервисного модуля 35899 атрибуты
  2444/2445/2448 (`refiningYieldNormalOres/MoonOres/Ice`) все три равны 0.50, а у ригов
  их нет вовсе, только общий 717. Наборы разные не потому, что считается по-разному, а
  потому что лунный кусок везут в нулевую Tatara, а вельдспар — на ближайшую НПС-станцию.
  Формула: `база × (1+0.03×3385) × (1+0.02×3389) × (1+0.02×профильный) × (1+импланты/100)`.
  **Выход считается ПО КАЖДОЙ РУДЕ отдельно**, потому что профильный навык у каждого
  семейства свой: у одного и того же альта 63.2 % на арконоре и 68.3 % на вельдспаре. Привязка руды к
  навыку — dogma-атрибут **790 `reprocessingSkillType`** на самой руде; CCP схлопнул
  старые «Veldspar Processing» в четыре (Simple/Coherent/Variegated/Complex Ore
  Processing, 60377–60380) плюс лёд, пять лунных редкостей, Mercoxit, Abyssal,
  Unrefined и Erratic. Бонус имплантов — атрибут **379 `refiningYieldMutator`**
  (Zainou 'Beancounter' RX-801/802/804 = +1/+2/+4 %), слот 8.
  Имя навыка в подсказке берём из sde, а НЕ из листа персонажа: неизученного навыка в
  листе просто нет, а назвать его надо именно в этом случае.
  ГРАБЛЯ: атрибут 2711 `oreBasicType` выглядит как готовый ключ семейства, но врёт —
  у `Veldspar IV-Grade` он указывает на себя, а не на `Veldspar`.
- **База переработки (структура + риг + секурити)** — `sde.RefineryModel`, все числа
  читаются из SDE, руками не вписаны:
  `база = выход рига × множитель секурити × (1 + бонус корпуса/100)`.
  Standup Reprocessing Facility I (35899) даёт `refiningYieldMultiplier` (717) = **0.50**;
  риг Reprocessing Monitor I (46639) = **0.51**, II (46640) = **0.53**, у них же
  множители секурити 2355/2356/2357 = **1 / 1.06 / 1.12** (нули и ВХ — одно значение);
  корпус несёт `strRefiningYieldBonus` (2722): Athanor **+2 %**, Tatara **+5.5 %**.
  ВАЖНО: множитель секурити — атрибут РИГА, поэтому без рига структура одинакова
  и в хайсеке, и в червоточине; у НПС-станции всегда ровно 50 %.
  Сверка: Tatara + Monitor II в нулях = 0.53×1.12×1.055 = 0.6262, а с идеальными
  навыками и имплантом +4 % это **90.63 %** — известный предел переработки в игре.
  XL-Set (для Tatara) и L-Set (для Athanor) по числам одинаковы, храним L-Set.
- **Считаем на единицу, показываем на объём.** В SDE количества даны на партию
  `portion_size`, поэтому всё делится на неё, а дальше умножается на `amount/volume`.
  Лазер режет кубометры, а не штуки: сравнивать руду можно только за м³ (лёд — за блок,
  лунную — за 1000 м³, иначе цифры нечитаемы).
- **Процент рядом с ценой** = «переработать или продать»:
  `стоимость минералов в ОДНОЙ единице / цена этой единицы − 1`. Универсальность даёт
  сравнимость: единица `Compressed Veldspar` (объём 0.001) перерабатывается ровно в то
  же, что единица сырого, а `Batch Compressed` (portion 1, материалы ×100) — в стократ
  больше. У газа материал компресснутого типа — сам газ, поэтому та же формула без
  единой правки даёт «выгода компрессии» (сверено с оригиналом: +29.58 % в цифру).
- **Семьи руд собираются ПО ИМЕНАМ.** ГРАБЛЯ: `variationParentTypeID` в SDE у руд пуст
  (CCP заполняет его кораблям и модулям), поэтому сорт ищется как «имя базы плюс одно
  слово» спереди («Brimful Bitumens») или сзади («Veldspar II-Grade»).
- **Бонус сорта берётся из НАЗВАНИЯ, а не из чисел** (`nominalGrade`): реальные
  количества целые и на пару десятых процента расходятся с номиналом (Mordunium II-Grade
  даёт 101 Pyerite там, где +5 % это 101.85). В колонках — что реально даёт игра.
  У `0-Grade` номинала нет, и он честно показывает −50 %.
- Колонки минералов у руды прибиты к восьми классическим: Morphite выпадает из одного
  Mercoxit и всё равно нужен, а новые минералы X-Grade руд добавляли бы по колонке
  прочерков — они уходят в «Прочее».
- Что нашлось сверх оригинала: `Prismaticite` и `Unrefined <минерал>` лежат НЕ в
  категории 25 (Asteroid), а в 4 (Material), группы 4915/4932 — они в `strayOreGroups`.
  Состав у них случайный (`type_materials_rand`), показывается середина диапазона.
- «Где копать» (`sde.foundIn`) в SDE НЕТ ВООБЩЕ — рукописная таблица, как `rawByPlanet`.
  Лунным семьям вместо неё подставляется редкость группы (R4…R64).
- Строка на КАЖДЫЙ сорт, имя семьи через `rowspan`. Стопка сортов внутри одной ячейки
  (как у оригинала) не выравнивается: строка с иконкой предмета втрое выше строки с
  числом, и подписи сортов уезжают от своих значений.
- **ВЁРСТКА: в этой таблице все строки обязаны быть одной высоты**, иначе она «плавает».
  Три правила, каждое выстрадано: (1) `white-space: nowrap` на ВСЕХ ячейках — перенос
  внутри одной растит всю строку; (2) вторая строка ценовой ячейки (`/м³`) рисуется
  ВСЕГДА, пустой при отсутствии — иначе строки с ценой выше строк без неё; (3) пометки
  вроде «случайный состав» — инлайном, а не блоком под именем. Иконка предмета в таблице
  ужата до 18 px под общий ритм. Проверять так: все `tbody tr` должны иметь одинаковую
  высоту (41 px), а `.otabwrap` — скроллиться сам, не разгоняя `body`.

**Инструменты → Наблюдение за рынком** (`/tools/market`) — вотчлист: PLEX, экстрактор
навыков, большой инжектор, топливные блоки H/N/O. По каждому — ордербук (шесть чисел)
и график дневных средних за 14/90/365 дней. Тип ищется по английскому имени

**Инструменты → Ордера** (`/tools/orders`, `internal/web/orders.go`) — игровой браузер рынка,
свёрстан по скриншотам окна «Торговая система»:
- слева дерево маркет-групп (`sde.MarketGroups`, таблица `market_groups`, 2106 групп; пустые
  насквозь ветки отрезаются, дерево рендерится в Go — рекурсия с open-path в шаблоне не
  живёт), раскрытие ЛОКАЛЬНОЕ (li.open, делегированный клик). **Товары выбранной группы —
  листья прямо в дереве** (после подгрупп, как в игре), сервер ходит только за `?g=` и `?t=`.
  Выбор товара через поиск сам раскрывает дерево до его группы (`TypeMarketGroup` →
  `MarketGroupPath`); тот же путь рисуется хлебными крошками над карточкой товара.
- вкладка «Цены»: продавцы СВЕРХУ (Количество/Цена/Место/Истекает через — срок из
  `issued+duration`), покупатели ПОД НИМИ (+Дистанция=range, Мин. объём) — стопкой, как в
  игре, не колонками. Книга — полная The Forge (`esi.RegionOrders`; PLEX автоматически в
  псевдорегионе), имена станций батчем, структуры через `LocationNames`. Ордера всех альтов
  матчятся по `order_id` (подсветка `.mine` + бейдж), отдельно таблица «свои ордера» — она
  видит и то, что вне The Forge. Выделение строк кликом: суммарное количество, среднее
  арифметическое цен и стоимость = количество × средняя цена; выделенные order_id живут
  вне DOM, MutationObserver возвращает выделение после ревалидационной подмены #main.
- вкладка «История цен» (`v=hist`): серверный SVG (`internal/web/histchart.go`) в стиле
  игры — точки средней за день, усы мин/макс, скользящие средние 5д (голубая) и 20д
  (оранжевая), канал Дончиана (20д rolling min/max, серая заливка), столбцы объёма внизу,
  подписи месяцев. Периоды `hd=30/91/182/365`, «В виде таблицы» `hv=t` (Дата/Кол-во
  ордеров/Количество/мин/макс/средн.). Данные — `esi.RegionHistoryFull` (полные свечи;
  `RegionHistory` отдаёт только средние).
- поиск типов — `sde.SearchMarketTypes`, индекс published-типов с маркет-группой в памяти
  (LIKE в SQLite не понимает кириллицу без регистра).

**Инструменты → Расчёт производства** (`/tools/build`, `internal/web/build.go`) — во сколько
обойдётся прогон чертежа, если ВСЕ комплектующие купить в Жите. Одним экраном: поиск →
параметры → счёт → вердикт.
- Поиск идёт по **имени чертежа И имени продукта**, на обоих языках: ищешь «Rifter», а
  находится «Rifter Blueprint». Индекс рецептов (4158 опубликованных manufacturing и
  reaction) держится в памяти (`sde.SearchRecipes`) — SQLite `LIKE` регистронезависим
  только для ASCII, и через базу русское имя не нашлось бы никогда.
- Всё состояние в адресной строке (`bp/runs/me/te/p/ch`), поэтому расчёт можно дать ссылкой.
  Постоянные настройки (система сборки, налог структуры, брокер, налог с продажи) живут в
  `app_settings` — они одни на все чертежи, как окно переработки у таблицы руд.
- Материалы — по перцентилям живого ордербука Житы (`esi.RegionOrderBook`), сбор за работу —
  по `adjusted_price` и индексу системы (см. «Формулы EVE»). Это РАЗНЫЕ цены, и путать их
  нельзя: EIV считается по базовым количествам без ME.
- Кнопка «Свои чертежи» подставляет ME/TE реальной копии из имущества альтов
  (`CharacterBlueprints` по всем персонажам параллельно), селект «Навыки времени» — срок
  работы с Industry/Advanced Industry выбранного альта.
- **Рекурсия «сделать или купить»** (`internal/web/buildtree.go`): счёт материалов — это
  дерево, у каждого узла своё решение, и решение ребёнка меняет цену родителя, поэтому
  дерево считается СНИЗУ ВВЕРХ. Режимы (`m=`): `buy` (покупаем всё, дефолт), `auto`
  (по каждому — что дешевле), `make` (строим всё, у чего есть чертёж). Клик по кнопке в
  строке фиксирует решение поимённо: списки id в `mk=`/`by=` перебивают режим и живут в
  ссылке. ME дочерних чертежей — один параметр `cme=`.
  - **ПРОГОНЫ ЦЕЛЫЕ.** Нужно 14 единиц, а чертёж делает по 100 — платишь за 100, излишек
    показан как «+86» и УЧТЁН в сравнении; иначе сравнение systematically врало бы в пользу
    сборки.
  - **Сбор за установку — на КАЖДУЮ работу.** Дерево из 8 компонентов это 9 работ, и сборы
    суб-работ входят в себестоимость компонента. Поэтому в итог идёт `matCost + jobFee`
    корня, а `SubFee` — только для разбивки: прибавлять его ещё раз = двойной счёт.
  - **ДВА РАЗНЫХ ЛИМИТА, потому что дорого разное**: `buildMaxTypes` 400 — сеть (один запрос
    ордербука на тип, типы собираются заранее одним обходом `collectTypes` и грузятся одним
    `RegionOrderBook`), `buildMaxNodes` 5000 — только CPU. Первая версия имела общий лимит
    400 узлов, и у Sabre половина компонентов молча показывалась как «нельзя сделать».
  - Глубина: `buy` раскрывает один уровень (этого хватает на подсказку «дешевле сделать»),
    `auto`/`make` — четыре; вручную отмеченный компонент раскрывается и глубже. Узел на
    уровень ГЛУБЖЕ лимита всё равно оценивается обеими ценами — иначе подсказки бы не было.
  - ISK/час считается по СУММЕ времени всех работ (финальная + суб-работы по очереди):
    прибыль во многом берётся из сборки компонентов, значит и время их работ в знаменателе.
  - Сверка на Sabre: покупка всех компонентов — 39.5M против рынка 36.2M (убыток), режим
    «считать выгоду» — 30.5M и маржа +13 %; Providence в auto — 1.24B против 1.75B, +34 %.
- ГРАБЛЯ ОБЪЁМА: `types.volume` у корпусов — объём В СОБРАННОМ ВИДЕ (Thrasher 43 000 м³),
  а упакованного в SDE нет вовсе. Корпуса-материалы в сумму объёма не входят и показывают
  прочерк — выдумывать таблицу упакованных объёмов не стали.
- ГРАБЛЯ ФОРМУЛИРОВОК: пока ордербук не подгрузился (stale-режим), цены пусты — страница в
  этом случае пишет «ордербук ещё грузится», а «в Жите этим не торгуют» только когда данные
  уже пришли. Иначе первый заход врал бы про рынок.
- Селект «Структура» в настройках — корпуса из SDE (`sde.IndustryStructures`), числа
  оттуда же; ключ хранится в `app_settings` (`build_struct`). Бонус материалов уходит и в
  дочерние узлы дерева, бонус времени — и в суб-работы.
- Что НЕ учитывается и написано на странице прямым текстом: риги структуры (ещё −2…2.4 %
  материалов и −20…24 % времени по группам предметов), стоимость самого чертежа
  (BPO/инвент), TE дочерних чертежей (суб-работам достаётся общий TE страницы).

**Инструменты → Управление флотом** (`/tools/fleet`) — единственная страница, которая
ПИШЕТ в игру. Данные всегда живые: `esi.Client.call` ходит мимо обоих ярусов кэша,
поэтому здесь нет stale-механики, зато есть галка «обновлять каждые 6 с» (свап `#main`
тем же приёмом, что и ревалидация; активная панель и галка восстанавливаются после свапа,
обновление пропускается, пока фокус в поле ввода).
Страница сама находит флоты: по каждому альту `/characters/{id}/fleet/`, группировка по
`fleet_id`, чтение — токеном босса (иначе 404, см. грабли). Четыре панели `.vnav`:
Состав (эскадры → эскадрильи → участники, корабли чипами), Управление (MOTD, свободное
перемещение, приглашение по имени или кнопкой для наших альтов вне флота), Доступ по
персонажам (живая проверка `GET /fleets/{id}/` токеном каждого — тот самый эксперимент
про «только босс»), Сырой ответ ESI.
**Хроника флота** — четвёртая панель той же страницы. **В API флота нет ни добычи, ни
лута, ни истории** — только текущий срез: кто, на чём, где, в доке или нет, роль,
`join_time`, флаг флотского варпа. Динамика получается ТОЛЬКО дифференцированием
последовательных чтений: `recordFleet` сравнивает каждый ответ `/members/` с сохранённым
состоянием (`fleet_state`) и пишет различия в `fleet_events` (join/leave/ship/system/
dock/undock/role/squad), `fleetHistory` сворачивает их в «стыковок / смен корабля /
переходов / времени в доке» на пилота плюс ленту. Для события `join` время берётся из
`join_time` ESI (точное), для остальных — момент чтения.
ГРАБЛЯ: кэш `/members/` — 5 с, поэтому после своей же записи (переезд между
эскадрильями) изменение видно только следующим чтением, событие опаздывает до 5 с.
Пишется, пока страница открыта; с галкой автообновления — каждые 6 с. Фоновых задач в
приложении по-прежнему нет.

Действия идут одним POST `/tools/fleet/action` (`op` = settings|move|kick|invite|
wing-create|wing-rename|wing-delete|squad-create|squad-rename|squad-delete), назначение
кодируется ключом `fc | wc:<wing> | sc:<wing>:<squad> | sm:<wing>:<squad>`
(`parseFleetTarget`). После успеха страница перезагружается.

**Инструменты → Планировщик навыков** (`/tools/skill-planner`, пакет `internal/skillplan`)
— калькулятор плана обучения: вставка плана в игровом формате (принимает и `Biology 4`,
и `Biology V`), пересборка порядка, подбор ремапа, оценка имплантов, экспорт обратно.
Планы лежат в `skill_plans`; **очередь навыков ESI не пишет**, готовый план копируется руками.
- **Источник плана** — вставленный текст ИЛИ кнопка «Очередь персонажа из игры»
  (`src=queue`): очередь из `/characters/{id}/skillqueue/` сама по себе валидный план,
  её незавершённые записи превращаются в строки и заполняют форму, копировать руками
  ничего не надо. Блок «Советы» — те же числа, но словами: ремап, топовый имплант
  (с проверкой уровня Кибернетики персонажа), самая медленная пара, выигрыш от
  перестановки, ускоритель, нераспределённые SP, упор в потолок.
- **Средняя дата готовности** (`MeanDone`) — вторая целевая функция рядом со сроком:
  общий срок от порядка не зависит, но «короткие вперёд» (SPT) минимизируют СРЕДНЮЮ
  готовность навыка. На живой очереди альта это дало −146 дней при том же сроке.
- **Стоимость уровня** = `ранг × (base[L] − base[L−1])`, где base — КУМУЛЯТИВНАЯ таблица
  `{250, 1414, 8000, 45255, 256000}`. Приросты: `{250, 1164, 6586, 37255, 210745}`.
  Пятый уровень один стоит в 4,6 раза больше первых четырёх вместе.
- **Скорость** = `основная + вторичная/2` SP/мин. ГРАБЛЯ: атрибуты навыка лежат в
  dogma 180/181 и содержат id 164–168 (харизма…воля), а НЕ 175–179 — те у имплантов.
  Каталог навыков — `sde.Skills()`, category_id 16, читается один раз в память.
- **Время плана = Σ SP/скорость**, сумма независимых слагаемых: **перестановка навыков
  не меняет срок вообще**. Меняет только состав и характеристики. Поэтому `Order()`
  оптимизирует «полезное раньше», а срок режут `Remap()` и импланты, и на странице есть
  отдельная таблица «где план теряет время» — разбивка SP по парам характеристик.
- **Пересортировка** (`Order`) — жадный топологический обход: на каждом шаге берётся
  самый дешёвый (или самый быстрый) из уровней, у которых уже выполнены предыдущий
  уровень и все пререквизиты. ГРАБЛЯ: наивная сортировка по цене выдаёт очередь,
  которую игра не примет — `Astronautics Rigging 1` (750 SP) дешевле `Jury Rigging 3`
  (13 172 SP), но требует его.
- **Ремап** (`Remap`) — полный перебор: база 17, 14 очков, максимум +10 в атрибут, всего
  1001 раскладка. Жадное «всё в основной» ошибается: вторичный атрибут стоит полочка
  за очко, и последние очки часто принадлежат ему (типовой ответ — 27/21).
- **Импланты**: `+3 … - Basic` требует **Cybernetics 1** (не 3!), `+4 … - Standard` —
  Cybernetics 4, `+5 … - Improved` — Cybernetics 5. Семейства: Ocular Filter (восприятие,
  слот 1), Memory Augmentation (память, 2), Neural Boost (воля, 3), Cybernetic
  Subprocessor (интеллект, 4), Social Adaptation Chip (харизма, 5).
- **Церебральный ускоритель** — бустер в слоте 10, требований навыков нет вовсе;
  `Биология` даёт +20 % длительности за уровень (у Genius 'Boost' база 12 суток → 19,2
  при Биологии 3). Считается как SP, набежавшие в окне сверх обычного темпа.
- Характеристики из ESI приходят **вместе с имплантами** (та же посылка, что на странице
  клонов), поэтому «текущие» и «после ремапа» сравниваются с одинаковым вкладом имплантов.

**Формат шаблона колонии EVE** (пакет `internal/pi`):
`Pln` тип планеты, `CmdCtrLv` уровень КЦ, `Diam` диаметр (км), `Cmt` комментарий;
`P[]` структуры `{T: тип постройки, La/Lo: радианы, S: производимый товар|null}`;
`L[]` связи `{S,D}` — индексы пинов **с единицы**; `R[]` маршруты `{P:[путь], Q, T}`.
**ГРАБЛЯ: импортёр игры придирчив к JSON** — обычный `json.Marshal` отвергается.
Нужен точный стиль клиента (`pi.Template.JSON()`): разделители `", "` и `": "`,
`Diam` ОБЯЗАТЕЛЬНО с десятичной точкой (`4460.0`), только ASCII в `Cmt`.
Шаблоны P0→P1 («создать все 15») строятся **пересадкой рецепта на готовую раскладку**
(`pi.Reskin` + донор `internal/pi/donor.go` — реальная компактная колония владельца):
координаты, связи и маршруты берутся как есть, меняются планета, типы построек
(по роли через `sde.StructureRole`) и товары. Экстрактор не ставится — его размещают
вручную по пятнам ресурсов. ОГРАНИЧЕНИЕ: генератор не проверяет CPU/PG командного центра
и длину линков.

## Деплой на RB5009 (arm64)

`.\deploy\build-arm64.ps1` → `dist\eve-empire-arm64.tar` (~13 МБ). Docker на машине нет
и не нужен: modernc SQLite — чистый Go, поэтому `GOOS=linux GOARCH=arm64 CGO_ENABLED=0`
даёт статический бинарник, а `cmd/mkimage` сам пишет тар формата `docker save`
(однослойный образ, «legacy»-раскладка `<layerid>/layer.tar` + manifest.json +
repositories — её понимают и Docker, и контейнерный движок RouterOS).

- **Корневые сертификаты кладём в образ руками** (`/etc/ssl/certs/ca-certificates.crt`,
  экспорт `Cert:\LocalMachine\Root`, 53 корня): в scratch-образе системного хранилища
  нет, а без него весь ESI отваливается по TLS. Проверено дозвоном до esi.evetech.net,
  developers.eveonline.com, images.evetech.net **только этим бандлом**.
- В main.go импортируется `time/tzdata` — в образе нет `/usr/share/zoneinfo`, и `TZ`
  без вшитой базы молча превращается в UTC.
- Путь к статике вынесен в `SDE_PATH` (был захардкожен `sde.db`): `sde.db` 250 МБ и
  рабочая база живут на USB-диске роутера, монтируются в `/data`, в образ не попадают.
- **ГРАБЛЯ: `.ps1` в UTF-8 без BOM** Windows PowerShell 5.1 читает как ANSI —
  кириллица в скрипте ломает разбор строк. Файлы скриптов сохранять с BOM.
- Порядок действий на роутере (пакет `container`, device-mode, veth+bridge, mounts,
  envs, `/container/add`) — в [deploy/README.md](deploy/README.md), команды выверены
  под **RouterOS 7.23.1**. ГРАБЛЯ: имена свойств контейнера менялись — в 7.21 `mounts=`
  стало `mountlists=`, а `name=` в `/container/mounts` — `list=`; все гайды в сети
  написаны под 7.1x и на 7.23 не примутся.
